# CI/CD

## Pipeline

`ci.yml` runs on every pull request and on pushes to `developer`. It installs Flutter 3.32.8, runs `pub get`, regenerates Drift/Freezed/JSON sources, checks that generated files are committed, formats, analyzes, tests, and uploads coverage.

Pushes to `developer` additionally run the Android and unsigned iOS development build workflows. There are no configured flavors, so each build uses the default Runner/Android release configuration. A push to `developer` never creates a production release.

Every push to `main` runs `release.yml`. A concurrency lock refreshes the latest `main`, calculates the next patch version and build number, validates, builds a signed Android APK/AAB with Flutter build overrides, then commits the new `pubspec.yaml` version, creates the matching tag, and creates or updates the GitHub Release. The version commit contains `[skip ci]`, so it cannot start another production release.

## Local checks

```bash
flutter pub get
dart run build_runner build --delete-conflicting-outputs
dart format --output=none --set-exit-if-changed .
flutter analyze
flutter test --coverage
flutter build apk --release
flutter build ios --release --no-codesign # macOS only
```

## GitHub configuration

Create `development` and `production` environments. Add these production secrets:

| Secret | Purpose |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | Base64-encoded release keystore |
| `ANDROID_KEY_ALIAS` | Android signing key alias |
| `ANDROID_KEY_PASSWORD` | Android key password |
| `ANDROID_STORE_PASSWORD` | Android keystore password |

The iOS workflow currently uses `--no-codesign`, so it needs no Apple secret and produces an inspection/build artifact, not an installable IPA. To distribute iOS, add an Apple Distribution certificate, provisioning profile, and App Store Connect API key to a protected environment, then replace that step with certificate/profile installation and an archive/export step. For Google Play, use a protected service-account secret and a gated deploy job using the generated AAB. This project currently has no Firebase files, `.env` files, or API secrets to configure.

### GitHub Variables

No repository or environment variables are required. The CI workflows pin `FLUTTER_VERSION` to `3.32.8` directly so toolchain changes are reviewed as code changes rather than silently changing builds.

## Versioning and releases

The current version is `1.0.2+2` in `pubspec.yaml`. Each successful `main` release increments the patch and build components: `1.0.2+2` becomes `1.0.3+3`. `pubspec.yaml` is the only version source. Flutter maps the name to Android `versionName`/iOS `CFBundleShortVersionString` and the build number to Android `versionCode`/iOS `CFBundleVersion`; the release build also passes both values explicitly to Flutter.

Do not create release tags manually for normal production releases. The workflow creates `v1.0.3` from `1.0.3+3`:

```bash
git checkout developer
git pull --ff-only
# Make and test changes, then open and merge a PR into main.
```

Use `developer` for integration, `main` for production-ready code, and `vX.Y.Z` tags generated by Actions. Protect `main`, require pull-request CI for merges, and require approval for the `production` environment. A rerun after a partial failure reuses an existing matching tag/release and does not duplicate it.

### First automated release

1. Create or rename the integration branch to `developer` if it does not already exist.
2. Add the four Android signing secrets and create the `production` environment.
3. Open a pull request from `developer` into `main` and wait for CI to pass.
4. Merge the pull request. With the current `1.0.2+2`, Actions builds `1.0.3+3`, commits that version, creates `v1.0.3`, and publishes the APK/AAB release.
5. Download the APK/AAB from the GitHub Release and verify the version shown by the installed app/store metadata.

To test CI safely, push a small change to `developer` or open a pull request. To test production without merging application changes, use a temporary protected test repository or a disposable `main` branch; the production workflow intentionally creates a real version commit, tag, and release.

## Troubleshooting

- A generated-source diff means the checked-in Drift/Freezed output is stale; run the build-runner command locally and commit the result.
- Android signing failures usually mean a keystore secret, alias, or password does not match. The keystore must be base64 encoded without line wrapping.
- iOS distribution cannot work with `--no-codesign`; configure the Apple certificate/profile and App Store Connect credentials in GitHub Environment secrets.
- CocoaPods failures can require updating the lockfile or the runner image. Run `cd ios && pod install --deployment` locally on macOS.
- If a release fails before the version commit, fix the cause and rerun the workflow; the repository version was not changed.
- If a release fails after the tag was pushed, rerun the original workflow. It verifies the matching version/tag and updates the existing GitHub Release assets.
- A tag/version mismatch stops the workflow rather than creating a duplicate or inconsistent release.
