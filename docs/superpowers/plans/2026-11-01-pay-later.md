# Pay Later Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Pay Later tabs to Monivo: purchases recorded as ordinary expenses linked to a tab, payments that settle them without touching budgets, an always-correct owed balance, settle rhythms with reminders, and overview/detail screens.

**Architecture:** New feature folder `lib/features/pay_later/` (Clean Architecture like `bills/`). Four new Drift tables (schema v9); no existing table changes. All money arithmetic in a pure `PayLaterAllocator`/`PayLaterLedger` pair working in integer minor units via `MoneyMath`. Expense integration is a wrapper use case (`TabPurchaseUseCase`) that nests the existing `ExpenseRepository` writes inside one Pay Later transaction, exactly as `PayBillUseCase` does today; the "Now" path through `ExpenseBloc` is untouched.

**Tech Stack:** Flutter, Drift (SQLite, FKs on), flutter_bloc, go_router, get_it, equatable, fl_chart, flutter_local_notifications, uuid. No new packages.

**Spec:** `docs/superpowers/specs/2026-11-01-pay-later-design.md` (approved 2026-11-01). Read it before any task; section numbers below (§n) refer to it.

## Review Focus

1. **3-decimal currencies (OMR):** three 0.350 meals and a 0.700 payment leave exactly 0.350 owed on the third meal and status "paid" on the first two — never 0.34999 or "partly paid". Owner: Task 3 test `omr three meals partial payment is exact`.
2. **Editing a tab purchase into another-currency budget:** today the form only *warns* on a currency-changing move; for a purchase on a tab the save must be *blocked* with the reason. Owner: Task 9 widget test `tab purchase cannot move to another currency`.
3. **Boundary days:** a purchase on a period's last day vs the settle-up day, a `monthly_day(31)` tab in February, and US DST day 2026-11-01 must land in the right period. Owner: Task 2 tests (run under both TZs).
4. **Double-tapping Save on the payment sheet** records one payment. Owner: Task 12 widget test `payment sheet saves once on double tap`.
5. **Budget delete with paid tab purchases:** no orphan rows, freed money is re-applied or becomes credit, and a second `reconcileAll` is a no-op. Owner: Task 8 test `budget delete reconciles touched tabs idempotently`.

Added after plan review (2026-11-02, user's five points):

6. **Budget delete is atomic:** a failure while reconciling rolls back the budget, its expenses, links and allocations. Owner: Task 8 test `budget delete rolls back entirely when reconcile fails`.
7. **Payment history balance matches the ledger** for back-dated payments and out-of-order entry. Owner: Task 2 property test `balanceAfter equals purchases to date minus payments to date`.
8. **One transaction across three repositories:** expense insert, budget remaining update and link insert commit or roll back together. Owner: Task 6 test `failed link insert rolls back expense and budget remaining`.
9. **Double submit and concurrency:** the same payment id twice gives one row; two different payments each equal to the owed amount give one success and one overpay error. Owner: Task 7 tests.
10. **Production wiring can't silently drop Pay Later:** new collaborators are required constructor parameters, and the DI test checks the wiring. Owner: Task 8.

## Transaction boundaries (one place to check them)

| Operation | One transaction contains | Then (outside) |
|---|---|---|
| Add purchase (Pay later) | expense insert + budget remaining update (existing repo, nested) + link insert + reconcile diff | notify `expenses`, `payLater`; reschedule tab reminder |
| Edit purchase | expense update (+ both budgets' remaining, existing) + link change + reconcile old tab + reconcile new tab | same |
| Delete purchase | read link snapshot + expense delete (cascades link + allocations) + budget remaining + reconcile tab | same |
| Undo delete | expense insert + link insert + reconcile | same |
| Record payment | payment insert + chosen (manual) allocations + reconcile | notify `payLater`; reschedule |
| Edit / delete payment | payment update/delete (cascade allocations) + reconcile | same |
| Create / edit / archive / delete tab | tab row write (delete only when no activity) | notify `payLater`; reschedule/cancel |
| Budget delete | **one** outer transaction: read touched tab ids → existing `deleteBudget` (its own transaction nests as a savepoint) → reconcile each touched tab | notify `budgets`, `expenses`, `payLater`; reschedule |
| Restore backup | existing `_replaceAll` transaction extended with the 4 tables + reconcile all inside it | reschedule tab reminders |

**Why nesting is safe (review point 3).** DI registers one `AppDatabase` singleton (`injection.dart:140`) and every datasource receives `getIt<AppDatabase>()`. Drift transactions are zone-bound to that database: any query issued inside `transaction(...)` on the same instance joins it, and a nested `transaction(...)` becomes a savepoint. `PayBillUseCase` already relies on this. The plan doesn't take it on trust: Task 4 adds a DI identity test, and Task 6 adds a rollback test across all three repositories.

**Crash recovery (review point 1).** Every multi-table write above is a single SQLite transaction, so an app kill mid-write rolls back completely and there is no window of inconsistency. `ReconcileTabUseCase.all()` still runs at app start as a safety net for anything outside these paths (e.g. a database edited by an older build). It is idempotent and is tested against a deliberately corrupted database.

**Double submit (review point 4).** Protection is in the use case and the database, not the button: the payment sheet generates the payment id once when it opens and passes it to `TabPaymentUseCase.record(paymentId:)`. Inside the transaction an existing row with that id returns the stored payment instead of inserting (the primary key also rejects a second insert, which is caught and resolved the same way). Drift runs transactions on one connection one at a time, so two different concurrent payments can't both pass the "not more than owed" check.

Period rules exactly as spec §4.

**`PaymentLine.balanceAfter` (review point 2).** Payments are ordered by `(paidDate, createdAt)`. For payment Pₖ paid on day D:

```
balanceAfter(Pₖ) = Σ amount of purchases dated ≤ D  −  Σ amount of payments P₁…Pₖ
```

This is not an approximation. Take the current allocation rows and filter them to payments P₁…Pₖ and purchases dated ≤ D. Then owed − credit over those rows is exactly this number, because the allocation terms cancel. So the balance shown in payment history always agrees with the allocation ledger, including:

- back-dated payments (recorded today, dated earlier), and
- payments whose money went to purchases dated after D (the balance is then negative = "in credit then").

The tab header shows today's owed or credit from the full ledger. When no purchase is dated after the last payment, the last payment's `balanceAfter` equals the header (owed − credit). A purchase dated on the payment day counts as before the payment. Display: positive → "Owed after: X", zero → "Settled", negative → "In credit after: X".

```dart
class AllocationDiff extends Equatable {
  final List<PaymentAllocation> inserts;
  final Map<String, double> updates; // allocation id → new amount
  final Set<String> deletes;         // allocation ids
  bool get isEmpty;
}

class PayLaterAllocator {
  PayLaterAllocator({required String currency, String Function()? newId, DateTime Function()? clock});

  /// Manual allocations for a new payment: chosen purchases in FIFO order,
  /// each capped at what it still owes. Leftover is left for [reconcile].
  List<PaymentAllocation> allocateChosen({required TabPayment payment,
    required List<ExpenseEntity> purchases, required List<PaymentAllocation> existing,
    required Set<String> chosenExpenseIds});

  /// Brings stored allocations back to the invariants (spec §3, §5).
  AllocationDiff reconcile({required List<ExpenseEntity> purchases,
    required List<TabPayment> payments, required List<PaymentAllocation> allocations});
}
```

`reconcile` algorithm (all in integer units):

```
1. delete allocations whose payment or purchase is not in the inputs
2. for each payment with applied > amount: trim its allocations —
     automatic before manual, then newest purchase first — until applied == amount
3. for each purchase with paid > amount: trim its allocations —
     automatic before manual, then latest payment first (paidDate, createdAt desc)
4. for each payment, oldest first (paidDate, createdAt), with unapplied > 0:
     for each purchase FIFO (date, time, createdAt) with owes > 0:
       take = min(unapplied, owes); add to existing (payment, purchase) row if present
       (update) else insert automatic allocation
5. return the diff against the input allocations (a row trimmed to 0 → delete)
```

  - `partial payment leaves the remainder owing on the next purchase`
  - `multiple payments continue where the last stopped`
  - `chosen purchases are paid first and marked manual; leftover goes fifo`
  - `allocation never exceeds what a purchase owes`
  - `payment amount reduced trims automatic before manual, newest purchase first`
  - `purchase amount reduced frees money, which moves to the next unpaid purchase`
  - `deleted purchase: freed money moves on; with nothing owing it stays as credit`
  - `invariant: after reconcile owed == 0 or credit == 0` (property-style loop over 200 seeded random scenarios with `Random(42)`)

## Known limitations (by design, from the spec)

- No recurring entries (Bills owns them); no multi-item purchases; no conversion between currencies.
- JSON/CSV export and import don't carry tab data; only full backup/restore does.
- `balanceAfter` in payment history is "as of that payment's date with today's data". Editing an old purchase changes the historical balances shown, because history is derived, not frozen.
